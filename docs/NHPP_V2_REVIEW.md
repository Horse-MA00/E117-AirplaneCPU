## 結果與適用範圍

在未參與開發／校準的 240 條新合成航班歷程上，v2 的 D28 突增情境保護覆蓋率為 **82.5%**。同一批資料上，沿用原有加 16 座規則的 v1 為 **30.0%**；讓 v1 也使用相同的新校準程序後則為 **80.0%**。因此不能把改善全部歸功於需求模型，也不能把不同資料批次的舊 47.62% 直接當作公平對照。

需求模型本身的原始 P90 在 D28 突增情境由 17.5% 提高至 47.5%，仍明顯低於 90%。提高至 82.5% 的部分來自另外的保護量校準；它是一項保守決策規則，不應標成機率 P90。這個實驗不證明真實 HK Express 市場的表現。

v2 在 D14／D7 的整體需求 MAE 下降，但 D28 整體需求 MAE 上升。沒有在看過最終測試後再調整參數來隱藏這項退步。

## 重現失敗與最小案例

先保存完整 v1 至 `simulation/baselines/nhpp_v1.py`。

```bash
python -m simulation.diagnose_nhpp
python -m simulation.diagnose_nhpp --minimal
```

上述兩個命令預設執行 v1，應保持失敗，作為診斷對照。以 seed 117 重播已經看過的 42 條突增歷程，保護覆蓋 18/42，即 42.86%，低於預先設定的開發門檻 80%。舊報告 47.62% 使用 forecast seed 271117，因此差異不能當作模型改進。

最小案例 SYN-00016 只保留 D64 至 D28 的 37 列已知快照：v1 保護 107 座，實際後續潛在需求 153。沒有將未來行或情境標籤傳進預測器。

修正後執行：

```bash
python -m simulation.diagnose_nhpp --model v2
```

得到 38/42，即 **90.48%**，原有開發回歸訊號轉綠。這批舊 holdout 已經看過，只作開發證據，不能再稱為新版本的獨立測試。

## 先列假設再驗證

1. **未來尚未發生的跳變。** 同一段已觀測歷史可以接上不同未來，無法從資料中確定下一次衝擊。需將未知跳變列為未來情境，而非假裝已識別它。
2. **長窗口將已發生跳變攤平。** 預測器可能把水準跳升誤當成會持續加速的指數斜率。
3. **容量截斷丟失資訊。** 售完可用座位只表示需求至少這麼多，不能把它當成精確需求，更不能將售罄後的零成交當成零需求。
4. **價格變動混入成長率。** 歷史價格變化會影響到達／購買需求，需明示價格反應假設。

逐項探測的資料在 `nhpp_v2_window_probe.json` 和 `nhpp_v2_ablation.json`。單純將窗口改為七天，開發 120 條歷程的 D28 MAE 從 26.50 惡化到 35.49，因此沒有採用「所有航班只看七天」的捷徑。

60 條開發歷程的單項消融顯示：移除未來情境會使 D28 突增 MAE 從 39.45 惡化到 57.01，原始覆蓋從 60% 降至 30%；但整體 MAE 反而較低，說明保守預測存在取捨。價格調整改善該探測集的 D28 整體 MAE，但不是每個時點或族群都改善。右截斷處理與轉折檢測在該小樣本上的平均增益不一致，因此只主張它們修正了觀測語義與指定回歸案例，不宣稱每個模組都全面提高準確率。

## v2 如何計算

- 過去最多 36 個完整區間的 gross bookings 作觀測，取消另外處理；只用指定時點以前的資料。
- 以 Gamma 需求水準與 beta 網格表示參數不確定性，允許負 beta。beta 範圍及先驗是工程假設。
- 歷史正常總價以假設彈性 0.8 調整 exposure；未來正常報價保持當前水準，不偷看生成器的未來價格。
- 對候選轉折點比較兩段 Poisson 計數的 likelihood；證據足夠時用轉折後資料重新估計水準，並收縮斜率，避免把突然增加誤當成永久指數加速。
- 可用位被買光的區間使用 `Pr(Poisson(mean) >= available)` 的右截斷 likelihood。完全售罄、沒有銷售曝光的區間不提供零需求證據。重要性抽樣有效樣本太少或大半歷史無法識別時，不釋放會員位。
- 每條未來路徑抽取固定水準、斜率，以及可能的持續衝擊／短暫衝擊時間。給定該路徑後是分段 NHPP；跨路徑是 NHPP 混合分布，不能稱為單一確定強度的 NHPP。
- 對已觀察到的上升保留回落可能性，未知未來衝擊也保留明示先驗。這些概率並非真實航空市場的估計。
- 每條路徑分開執行容量限制與取消，最後統計空座期望及 P10/P90。

固定參數完整保存在校準與測試 JSON 的 `settings` 欄位。以已知七天水準從 1 增至 7 的回歸案例，v1 預測未來約 377 次請求；v2 識別水準轉折後預測約 191，接近持續每天 7 次的 28 天基準 196，並保留未來風險。

## 參數與輸出（對照 `backend/nhpp.py`）

以下數值與程式一致；模型凍結，修改需新版本與新驗證種子。

### 輸入與輸出

入口是 `backend.nhpp.forecast(rows, days_to_departure, seed)`。

輸入只限同一航班截至決策時的歷史：容量、訂位、完整票價、gross bookings、取消及區間長度。程式先移除未來列，再使用最近約 35 日的完整區間；目前邊界採包含端點，最多可納入 36 個每日區間。

| 輸出 | 含義 |
| --- | --- |
| `beta`、`rate_now` | 當前趨勢及需求水準的抽樣平均 |
| `expected_remaining_demand` | 從現在到停售的正常潛在請求期望；可以超過剩餘座位 |
| `expected_empty_seats`、`expected_empty_rate` | 考慮容量及取消後的停售空座期望 |
| `demand_p10`、`demand_p90` | 模型下剩餘需求的分位數 |
| `raw_protection_p90` | 正常需求原始上側分位數 |
| `protection_allowance`、`protection_p90` | 額外校準保護量及加總後的操作保護量 |
| `releasable_seats` | 通過資料品質及保護限制後的可釋位 |
| `forecast_curve` | 未來訂位期望與分位數路徑 |
| `demand_curve`、`protection_curve` | 同一批模擬路徑的未來剩餘需求及保護量 |
| `diagnostics` | 變點、截斷比例、有效抽樣數、校準與情境假設 |

**NHPP 不輸出會員票價 P 或年費 V。** 它為後續政策提供正常需求與容量風險依據。

目前 NHPP 也不直接把航線、星期、節假日或旅客分類當作回歸特徵。預測未來正常需求時，假定正常完整票價維持目前參考水準；它沒有另一個預測未來正常票價曲線的模型。

### 基礎強度與參數估計

以決策時刻為相對時間零點，基礎強度為 `rate × exp(beta × t)`。過去每個區間再按當時完整票價與目前參考票價之比，調整需求曝光。

實作使用：

1. **beta 網格**：181 個點，範圍 `[-0.08, 0.10]`，允許需求下降及上升。
2. **beta 先驗**：中心 `0.012`，一般標準差 `0.025`；偵測變點後使用 `0.018`。
3. **水準先驗／後驗**：Gamma–Poisson 結構；未截斷區間更新計數及加權曝光。
4. **不確定性抽樣**：先產生 2,400 個參數 proposal，再按權重重抽 800 條預測路徑。

這些參數是目前程式的研究設定，不是航空業已證實的 beta 上下界。也不是用全部合成資料做監督式「票價標籤訓練」；NHPP 會對每班航班的當時歷史重新推斷需求參數。

### 售罄造成的觀測截斷

如果某區間只有 5 位可售，最後賣出 5 位，只能知道需求至少為 5，不能知道需求恰好為 5。

- 未售罄：使用 `Pr(D = 觀測訂位數)` 的 Poisson 似然。
- 達容量：使用 `Pr(D ≥ 可售容量)` 的右截斷似然。
- 區間開始已無位：跳過該段零售票，不當成「有供應但沒有需求」。

程式使用較寬的需求水準 proposal 及重要性加權處理截斷，並輸出有效抽樣數 ESS。這改善售罄資訊的使用，但目前仍缺少會員在日內買光座位後的精確正常客可售時間，詳見限制。

### 如何處理需求突然增加

模型有兩層處理：

**已經發生的改變：變點偵測。** 比較最近 3／5／7／10／14 日與較早區間的需求水準。需要足夠區間及計數；對數似然比至少為 5，而且水準比達到上升 `1.8` 倍或下降至 `0.55` 倍以下，才接受候選變點。若偵測到改變，使用變點後資料重新估計水準及趨勢。

**尚未發生的改變：未來風險情境。** 預測路徑可包含沒有新衝擊、持續突增、短暫脈衝，或已觀察上升後回落。D28 無已知變點時，持續／脈衝的基準機率分別為 `0.22`／`0.10`；倍率範圍為 `2–4` 倍。實際機率按剩餘天數及是否已有變點調整。

因此模型可以反映「可能突然增加」的不確定性，但不能從相同歷史提前知道哪一天必然發生未知事件。

### 從需求到空座分布

每條路徑逐日抽樣正常請求及取消，並施加實際容量限制。概念上：

\[
B_{t+1}=B_t+\min(D_t,C-B_t)-X_t
\]

其中 `C` 是容量、`B` 是訂位、`D` 是潛在請求、`X` 是從期初訂位抽出的取消。最後計算各路徑的 `C - B_final`。

「需求 100、只剩 60 位」不會變成賣出 100 位；但剩餘需求仍可報為 100，保留供應不足的訊息。空座期望也不簡化成 `max(空位 - 平均需求, 0)`，因為容量截斷和取消具有非線性。

### 校準、保護與釋位

首先從 800 條路徑取得原始需求上側分位數 `q90`，再加上獨立校準集得到的保護修正：

\[
H_d=q_{90,d}+\left\lceil a_d\max(10,q_{90,d})\right\rceil
\]

`a_d` 在 D28／D14／D7 分別校準：對不同合成情境計算相對低估殘差的上側次序統計量，再取最保守情境的係數。執行時同一時點所有航班共用係數，不把航班情境標籤交給預測器。其他決策日使用相應較長校準時點的係數。

操作保護量 `H` 的欄位雖沿用 `protection_p90`，**不能把加了校準修正的數值稱為理論保證的 90% 後驗分位數**。

在資料品質條件成立時：

\[
Q_{\text{available}}=\max(0,\text{目前空位}-H_d)
\]

若到達停售、歷史不足、超過一半區間無供應／受容量截斷，或 ESS 小於 20，程式不釋出會員位。正常需求保護按 gross 請求計算，不先依賴未來取消來擴大會員供應。

**純示意例子：** 現在剩 60 位、原始需求分位數 24、額外保護 6，則可釋位為 30；政策選擇 75% 時，D28 首輪目標未售配額為 `floor(30 × 0.75) = 22`；D14／D7 再扣除前輪仍有效的未售配額，見[三輪放票](THREE_ROUND_RELEASE.md)。這不是任何真實航班的決策結果。

## 校準與最終測試協議

| 用途 | 生成種子 | 航班數 | 是否用來改模型 |
| --- | ---: | ---: | --- |
| 開發 | 20261114 | 180 | 可以；保留試驗記錄 |
| 校準 | 20261115 | 240 | 僅按照已選定規則估計保護 guard |
| 最終測試 | 20261116 | 240 | 不可以；一次打開後不再調參 |

各階段的航班身份由「生成種子＋flight_id」共同定義；雖然顯示 ID 會重用，隨機參數和歷程獨立生成。相同 final 航班及 forecast seed 117 同時交給 v1／v2；每個模型的亂數消耗方式不同，所以不宣稱兩者抽到了完全相同的預測路徑。

D28、D14、D7 分別校準。在每種已知合成情境計算 `(actual - raw_P90) / max(10, raw_P90)` 的 90% 上側次序統計量，取最保守的一組作該時點的全局 guard。**所有 runtime 航班使用同一個時點 guard；情境標籤只在校準與評分時使用。** v1／v2 使用相同校準規則，避免只替新模型增加保護裕量。

較短或非標準 horizon 使用下一個較長已驗證 horizon 的規則；這些中間點與從舊時點投射的 suffix protection 並未逐一獨立校準，發布未來優惠時仍須重新預測。只稱為保守工程做法，不保證逐時點覆蓋率。

模型、設定和原始碼 hash 必須與校準檔匹配；若過期，API 拒絕自動使用 guard。`raw_protection_p90`、`protection_allowance`、`protection_p90` 分別保留原始分位數、額外保護量及最終決策保護量。

```bash
python -m simulation.evaluate_nhpp_v2 development
python -m simulation.evaluate_nhpp_v2 calibration
python -m simulation.evaluate_nhpp_v2 final
```

最終報告已存在時第三個命令會拒絕重跑，防止反覆查看同一 holdout 後調參。未來新版本需要新的預先指定 final seed；不得刪除現有報告來冒充首次驗證。

## 已觀察與未知跳變

D14 已發生跳變的 13 班航班，原始覆蓋率由 61.54% 提高至 76.92%，需求 MAE 由 33.88 降至 22.13。這是更新觀測後模型改善的證據。

D7 尚未發生跳變的 12 班航班，v2 校準保護覆蓋卻由 v1 的 91.67% 降至 **75.0%**，仍有明顯缺口。不能只展示整體 98.75% 覆蓋而忽略這個族群。

逐日回放另抽取 final 的 20 班 surge，偵測到 50%；在成功偵測者中，中位延遲為 2 天，跳變前誤報率為 0%。這不代表所有航班都能在兩天內辨認跳變；未偵測到的情境包含售罄截斷及證據不足。

## 風險仍未消失

若假設釋出的會員位全部售出，D28 的平均新增正常需求擠出量由 v1 的 0.158 增至 v2 的 0.288 座／班；D7 由 0 增至 0.017。這項指標是容量壓力診斷，沒有計入會費與票價，不是財務損失。v2 較多釋出帶來額外風險，不能宣稱所有安全指標都改善。

下一步應優先取得真實曝光、售罄時間、促銷及購買請求資料，估計價格反應及轉折先驗；對未知跳變使用可設定的商業風險容忍度，並在新資料批次驗證。尚未校準的中間時點、極端需求和團體 all-or-nothing 訂位仍需專門驗證。

## 介面與驗收

`forecast(rows, days_to_departure=28, seed=117, protection_allowance=None)` 保持相容。新增 `demand_curve`（未受容量截斷的剩餘需求均值）和 `protection_curve`（相同未來路徑的剩餘需求保護）。定價模組應使用這些曲線，不能再用一個 beta 推算所有時點的強度。

模型測試涵蓋未來資料隔離、連續負 beta、階梯下降、已觀察水準跳升、右截斷 likelihood、取消分離、停售、過期校準拒絕，以及需求 suffix 的單調性。原有定價與庫存測試亦需通過。

所有 probe／報告在 `simulation/generated/nhpp_v2_*`；沒有保留臨時 debug logging。`simulation/diagnose_nhpp.py` 是可重跑的故障對照工具，故意保留 v1 的 red 行為。
